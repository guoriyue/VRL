# SPRINT：从 Slime 拆解 Continuous Rollout Queue

状态：proposed。

Repo reality update:

- Current config path is `trainer.rollout_orchestration`, not top-level `rollout_orchestration`.
- Current valid modes are `strict_on_policy` and `one_batch_overlap`.
- Current factory lives in `vrl/rollouts/orchestration/schedule.py`.
- Current orchestration config lives in `vrl/trainers/core/types.py::RolloutOrchestrationConfig`.
- Cross-node rollout is the primary hardware path that makes continuous useful: trainer GPU on the driver/head node, rollout GPUs on remote Ray worker nodes, Ray cluster provided externally through `RAY_ADDRESS`.

## 一句话目标

在 `one_batch_overlap` 之后，增加一个真正 continuous 的 rollout producer：producer 常驻后台持续生成、reward、写入 bounded queue；trainer 不再每 step 主动发起整批 rollout，而是从 ready queue 里取可训练 batch。

## 能解决什么，不能解决什么

这个 sprint 真正解决的是 rollout/trainer 阶段同步造成的 GPU 空档：

```text
rollout GPU 在 trainer step 期间没活干
trainer GPU 在 rollout collect/reward 期间没活干
trainer 每 step 都等整批 rollout 完成
rollout/reward 抖动导致 trainer 间歇性饿数据
```

它成立的前提是 rollout 和 trainer 有可并行资源：

```text
separate trainer/rollout GPUs
cross-node Ray rollout with trainer on head and rollout workers on remote GPUs
or at least partially independent CPU/reward/artifact work that can overlap training
```

它不能单独解决：

```text
single GPU 上 rollout 和 trainer 都需要独占同一份显存
rollout runtime 必须完全释放后 trainer 才能恢复
weight sync 或 actor startup/shutdown 是主耗时
reward model 本身是唯一瓶颈且没有独立资源
```

如果是 single-GPU handoff，continuous queue 只能暴露 `queue_wait_s`、`release_runtime_s`、`weight_sync_s` 等瓶颈，不能让两个 full-GPU 阶段真实并发。

边界锚点：

```text
target == Slime fully_async_rollout / rollout_buffer style continuous producer
target != strict on-policy
target != shallow one-batch overlap
target != vLLM/SGLang low-level engine scheduler
```

这个 sprint 不是替代 `SPRINT_engine_orchestration_from_slime.md`，而是它的下一层。前置 sprint 负责：

```text
rollout_id
policy_version
weight sync lifecycle
one_batch_overlap
RolloutIteration metadata
```

本 sprint 负责：

```text
continuous producer
bounded ready queue
bounded stale policy
queue backpressure
trainer drain protocol
weight sync barrier with running producer
```

## Slime 对照

Slime 有两种 async：

```text
train_async.py
  shallow one-batch overlap

examples/fully_async + slime_plugins/rollout_buffer
  continuous rollout producer / rollout queue
```

`examples/fully_async/fully_async_rollout.py` 的核心是：

```text
global AsyncRolloutWorker
  thread + asyncio loop
  active_tasks
  output_queue
  continuously pull prompts
  generate_and_rm_group(...)
  push completed groups into queue

generate_rollout_fully_async(...)
  drain output_queue until enough groups
```

对应代码语义：

```text
while running:
  while active_tasks < max_concurrent_tasks:
    samples = data_buffer.get_samples(1)
    task = generate_and_rm_group(...)
    active_tasks.add(task)

on task done:
  output_queue.put(group)

trainer call:
  get_completed_groups()
  return enough groups
```

`slime_plugins/rollout_buffer` 更接近生产形态：

```text
Rollout Buffer server
  /start_rollout
  /buffer/write
  /get_rollout_data

Generator process
  read prompt file
  call rollout engine
  compute reward
  write completed item to buffer

Trainer rollout function
  poll /get_rollout_data
  select enough groups
  convert to Sample
  push into local data_buffer
```

关键启发：

- producer 和 trainer 生命周期分离。
- ready queue 需要 group 概念，不是单 sample 随便拼。
- trainer 可以等 queue ready，也可以从 queue 中选择最新的 groups。
- buffer 必须暴露 meta info，否则无法知道 producer 是否健康。
- full async 是系统协议，不是简单 `asyncio.create_task`。

## 为什么不能直接跳过去

full continuous rollout 会让训练语义从：

```text
batch generated by current policy
```

变成：

```text
batch generated by some recent policy snapshot
```

所以必须先有：

```text
rollout_policy_version
trainer_policy_version
max_stale_policy_versions
old_log_prob availability
drop stale batch rule
weight sync barrier
```

没有这些，continuous queue 会悄悄变成无约束 off-policy training。

## 数据结构

### `ContinuousRolloutItem`

一个 completed prompt group 或 micro batch。

```text
item_id
rollout_id
request_id
group_key
rollout_policy_version
created_at
submitted_at
completed_at
prompt_count
sample_count
batch
metrics
metadata
```

`batch` 是 `RolloutBatch` 或可恢复的 path-backed artifact handle。第一版不要把 GPU tensor 放进 queue。

### `ContinuousRolloutQueue`

bounded ready queue。

```text
max_ready_items
max_ready_samples
max_ready_bytes
drop_policy
```

必须支持：

```text
put(item)
drain_for_iteration(...)
drop_stale(...)
stats()
close()
```

### `ContinuousRolloutProducerState`

```text
running
paused_for_weight_sync
current_policy_version
inflight_count
ready_count
last_submit_time
last_complete_time
last_error
```

### `StalenessPolicy`

```text
max_stale_policy_versions
allow_mixed_policy_in_iteration: false
drop_too_stale: true
```

第一版必须要求：

```text
one RolloutIteration consumes exactly one rollout_policy_version
```

如果 queue 里有多个 version 的 items，consumer 只能选择同一个 version 的 enough groups。否则等待、drop stale、或 fail fast。

## Config 形状

当前 repo 的配置入口是：

```yaml
trainer:
  rollout_orchestration:
    mode: strict_on_policy
    max_pending_rollouts: 1
    require_separate_gpus: true
    weight_sync_barrier: before_sync
```

continuous 必须挂在同一个路径下，不新增 top-level `rollout_orchestration`。

建议新增 preset：

```text
configs/base/rollout_orchestration/continuous.yaml
```

安全第一版：

```yaml
trainer:
  rollout_orchestration:
    mode: continuous
    max_pending_rollouts: 2
    require_separate_gpus: true
    weight_sync_barrier: pause_admission_and_drain_inflight

    continuous:
      max_inflight_groups: 1
      prefill_target_groups: 1
      min_ready_groups: 1
      max_ready_groups: 2
      max_ready_bytes_mb: 8192

      # Phase A default: behavior-equivalent to strict on-policy.
      max_stale_policy_versions: 0
      allow_mixed_policy_in_iteration: false
      drop_policy: drop_oldest_stale

      producer_runtime: in_process      # in_process | ray_actor
      queue_storage: cpu                # cpu | path

      wait_timeout_s: 300
      queue_poll_interval_s: 0.05
```

真实 cross-node throughput run 可以用 override 打开 bounded stale：

```bash
RAY_ADDRESS=<head-ip>:6379 CUDA_VISIBLE_DEVICES=0 python -m vrl.scripts.train \
  --config experiment/diffusion/sd3_5/online_grpo_ocr \
  /base/distributed=ray_rollout_cross_node \
  /base/rollout_orchestration=continuous \
  trainer.rollout_orchestration.continuous.max_stale_policy_versions=1 \
  trainer.rollout_orchestration.continuous.max_inflight_groups=4 \
  trainer.rollout_orchestration.continuous.max_ready_groups=8
```

注意：`RAY_ADDRESS` 是部署环境输入，不写进 YAML；机器清单、SSH、Ray cluster lifecycle 仍由 Ray / infra 层管理。

含义：

```text
max_inflight_groups
  producer 同时发起多少 group collect。

prefill_target_groups
  启动训练前 queue 至少预填多少 group。

min_ready_groups
  trainer 一次 drain 至少需要多少 prompt groups。

max_ready_groups / max_ready_bytes_mb
  backpressure 上限。

max_stale_policy_versions
  trainer 当前版本和 rollout batch 版本的最大差距。

weight_sync_barrier
  sync weights 前暂停提交新任务，并处理 in-flight。continuous 下唯一允许值是
  `pause_admission_and_drain_inflight`。
```

## Producer 协议

producer 常驻运行：

```text
start()
  ensure initial rollout weights
  start background task

loop()
  while running:
    if paused:
      sleep
      continue

    drop stale ready items

    while inflight < max_inflight and queue below high watermark:
      prompts = prompt_source.next_group()
      submit collect task with current_policy_version

    harvest completed tasks
    put completed items into ready queue
```

注意：

- producer 调用 `RolloutCollector.collect(...)`，不直接调用 generation runtime。
- reward 仍在 collector 内完成。
- producer 不计算 advantage。
- producer 不调用 evaluator。
- producer 不调用 algorithm。
- producer 不触碰 optimizer。

## Consumer 协议

trainer 每 step 调用：

```text
iteration = await continuous_schedule.next_iteration(...)
```

consumer 行为：

```text
1. 读取 trainer 当前 policy_version。
2. 从 ready queue 选择同一 rollout_policy_version 的 enough groups。
3. 检查 staleness <= max_stale_policy_versions。
4. 组装 RolloutIteration。
5. 从 queue 删除已消费 items。
6. 把 iteration.batches 交给 trainer 原有 train path。
```

如果 queue 不够：

```text
wait until enough groups or timeout
```

如果 queue 太旧：

```text
drop stale items
record dropped_stale_count
continue waiting
```

## Weight Sync 协议

这是 full continuous rollout 最容易出 bug 的地方。

第一版使用安全协议：

```text
before weight sync:
  producer.pause_admission()
  wait inflight tasks finish OR cancel if configured
  queue completed old-version items if stale policy allows
  sync weights to generation runtime
  producer.current_policy_version = runtime.current_policy_version
  producer.resume_admission()
```

不允许：

```text
while generation task is running:
  mutate worker weights
```

原因：否则一个 `GenerationRequest` 可能中途混入两个 policy。当前 `GenerationRequest.policy_version` 和 Ray worker guard 只能保证 worker entry 版本，不保证中途 mutate 后的连续一致性。

后续如果 generation workers 支持 immutable policy snapshot / LoRA slot swap，可以再放宽这个 barrier。

## Policy Version 语义

每个 produced item 必须记录：

```text
rollout_policy_version
trainer_policy_version_at_consume
stale_policy_versions
```

计算：

```text
stale_policy_versions = trainer_current_policy_version - rollout_policy_version
```

规则：

```text
if stale_policy_versions < 0:
  fail fast

if stale_policy_versions > max_stale_policy_versions:
  drop item

if item missing old_log_prob / trajectory signal needed by algorithm:
  fail fast
```

第一版建议：

```text
max_stale_policy_versions: 0
allow_mixed_policy_in_iteration: false
```

`max_stale_policy_versions: 1` 是 cross-node throughput mode，不是 Phase A 默认值。

## Artifact 和内存策略

visual rollout 的 artifact 很大，不能照搬 text-only Slime queue。

Queue item 不应该保存：

```text
GPU tensors
live model handles
diffusers mutable pipeline state
Ray actor handles
```

允许保存：

```text
CPU tensors
path-backed videos/images
trajectory tensors moved to CPU
small metadata
reward scalar / reward breakdown
old log probs
```

如果 `videos` 很大，第一版应支持：

```text
queue_storage: path
```

也就是 queue 里只存 artifact path / manifest，trainer consume 时再 materialize training tensors。

不要把 continuous producer 和 prompt dataset 写死。

抽象：

第一版可以包装当前 `OnlineTrainer.prompts`：

## 和 cross-node rollout 的关系

continuous queue 不负责创建 Ray 集群，也不管理机器清单。它只复用已经存在的 rollout runtime。

推荐组合：

```bash
RAY_ADDRESS=<head-ip>:6379 CUDA_VISIBLE_DEVICES=0 python -m vrl.scripts.train \
  --config experiment/diffusion/sd3_5/online_grpo_ocr \
  /base/distributed=ray_rollout_cross_node \
  /base/rollout_orchestration=continuous
```

资源边界：

```text
cross-node rollout:
  owns trainer/rollout GPU separation and Ray placement validation

continuous rollout:
  owns producer cadence, ready queue, staleness, and sync barrier

training config:
  declares resource budgets and rollout orchestration mode

environment:
  provides RAY_ADDRESS, CUDA_VISIBLE_DEVICES, VRL_DATA_ROOT, HF cache, etc.
```

不要在 continuous sprint 里新增：

```text
distributed.ray.address
distributed.cluster.hosts
distributed.cluster.ssh_key
```

这些属于 cross-node deployment/runbook，不属于 orchestration logic。

## Phase 1：类型和 queue

新增：

```text
vrl/rollouts/orchestration/continuous/types.py
vrl/rollouts/orchestration/continuous/queue.py
vrl/rollouts/orchestration/continuous/staleness.py
```

完成标准：

- Queue 有 max item / max sample / max bytes backpressure。
- Queue item 必须带 `rollout_policy_version`。
- `drain_for_iteration(...)` 不会混 policy version。
- stale item 会被 drop 并计数。

Phase A 的 queue depth / stale 配置必须能退化成 strict-equivalent：

```text
max_stale_policy_versions=0
max_inflight_groups=1
max_ready_groups=1 or 2
```

## Phase 2：in-process continuous producer

新增：

```text
vrl/rollouts/orchestration/continuous/producer.py
```

第一版用 in-process `asyncio.Task`，不是 Ray actor。

完成标准：

- producer 可以 `start()` / `pause()` / `resume()` / `stop()`。
- producer 能持续提交 `RolloutCollector.collect(...)`。
- producer respects `max_inflight_groups`。
- producer respects queue high watermark。
- producer error 会进入 state，而不是静默死掉。

## Phase 3：trainer consumer integration

新增：

```text
vrl/rollouts/orchestration/continuous/consumer.py
```

完成标准：

- `RolloutScheduleMode` 增加 `CONTINUOUS = "continuous"`。
- `RolloutOrchestrationConfig` 允许 `mode="continuous"`。
- `build_rollout_schedule()` 在 continuous 下返回 `ContinuousRolloutSchedule`。
- `OnlineTrainer` 不应该长出 continuous 专用分支；它继续只调用 schedule protocol。
- trainer train path 仍然复用已有 advantage/evaluator/algorithm 逻辑。
- 如果 queue 空，trainer 等待并记录 wait time。
- 如果 timeout，fail fast。

## Phase 4：weight sync barrier

目标：continuous producer 和 weight sync 不互相踩。

完成标准：

- `after_train_step(...)` sync 前会暂停 producer admission。
- in-flight collect task 会 finish 或按配置 cancel。
- sync 后 producer 用新 `current_policy_version` 提交新任务。
- ready queue 中旧 item 只有在 `max_stale_policy_versions` 允许时才能被消费。
- `RolloutOrchestrationConfig.__post_init__` 对 continuous 允许
  `weight_sync_barrier="pause_admission_and_drain_inflight"`，对其它 mode 继续要求
  `before_sync`。

## Phase 5：artifact storage

目标：支持 visual artifact 不撑爆内存。

完成标准：

- Queue stats 能估算 ready bytes。
- 支持 `queue_storage: cpu`。
- 支持 `queue_storage: path` 的接口设计。
- path-backed item 有 manifest，可定位 image/video/replay tensors。

第一版 path storage 可以只实现 manifest contract，不强制所有 collector 立即迁移。

必须记录：

```text
continuous.producer_inflight

continuous.queue_ready_samples
continuous.queue_ready_bytes
continuous.queue_wait_s
continuous.item_age_s
continuous.stale_policy_versions
continuous.dropped_stale
continuous.dropped_backpressure

```

完成标准：

- `TrainStepMetrics.phase_times` 能看到 queue wait。
- JSONL/debug metrics 能看到 producer 和 consumer 的 policy version。
- 能判断瓶颈是 rollout 慢、reward 慢、queue 不够、train 慢、还是 sync barrier 太频繁。

## Phase 7：Ray actor / external buffer

这不是第一版必须。cross-node rollout 已经通过 Ray generation actors 把真正的 generation
重活放到远端 worker；Phase A 的 in-process producer 只是调度远端 collect，足够验证
continuous queue 的语义和收益。Ray actor producer 是隔离/生产化增强，不是 cross-node
continuous 的前提。

目标：

```text
ContinuousRolloutProducer 可以跑在 Ray actor 中
trainer 和 producer 通过 Ray object / queue API 通信
```

原因：

- in-process producer 和 trainer 共享 Python process，debug 简单但隔离不够。
- Ray actor producer 更接近 Slime Rollout Buffer server。
- 以后可以把 reward model / artifact materialization 放在独立资源上。

完成标准：

- Ray actor producer 暴露和 in-process producer 一样的 API。
- Consumer 不关心 producer 是 in-process 还是 Ray actor。

## 最小完整交付

```text
1. Add continuous rollout item/queue/staleness types.
2. Add in-process producer with bounded inflight and ready queue.
3. Add consumer that drains same-policy ready groups.
4. Add weight sync barrier: pause admission, drain/cancel inflight, sync, resume.
5. Add config mode: trainer.rollout_orchestration.mode=continuous.
6. Add stale policy: max_stale_policy_versions=0 by default, no mixed-policy iteration.
7. Add queue metrics and debug JSONL fields.
8. Prove fake runtime benchmark:
   strict_on_policy time > one_batch_overlap time > continuous time after warmup.
```

Phase A acceptance bar:

```text
mode=continuous + max_stale_policy_versions=0 must be behavior-equivalent to strict_on_policy.
Default config must remain strict_on_policy.
Continuous preset must be opt-in.
Cross-node continuous usage must require only RAY_ADDRESS plus YAML/dotlist resource budgets.
```

## 明确非目标

本 sprint 不做：

```text
不实现 vLLM/SGLang continuous batching
不支持无限 stale replay
不允许一个 RolloutIteration 混多个 policy version
不把 advantage/evaluator/algorithm 放进 producer
不把 GPU tensors 长期放进 queue
不要求第一版支持 external HTTP buffer server
不要求第一版支持 Ray actor producer
```

## 判断标准

完成后，repo 应该能回答：

```text
producer 什么时候跑？
producer 用哪个 policy version？
queue 里有多少 ready data？
trainer 为什么选这个 batch？
这个 batch stale 几个 policy version？
weight sync 时 producer 是否还在写旧 worker？
如果 queue 爆了，drop 了什么？
如果 queue 空了，trainer 等了多久？
```

期望答案：

```text
Continuous producer owns rollout production cadence.
Queue owns ready data and backpressure.
Consumer owns same-policy batch selection.
Schedule owns weight sync barrier and staleness policy.
Trainer owns advantage, replay, loss, and optimizer update.
Generation runtime only executes pinned-policy requests.
```
